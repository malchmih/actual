# OP credit-card transaction identity through Enable Banking

Research for [malchmih/actual#3](https://github.com/malchmih/actual/issues/3), checked 2026-11-16. This note uses public provider/bank documentation, schemas, one public Enable Banking support comment, and a pinned Actual source snapshot. No live budget data or personal financial evidence was accessed.

## Bottom line

The public sources do **not** establish that an OP credit-card transaction exposed through Enable Banking always has a stable transaction identifier, or that its pending and booked forms share one. Enable Banking documents `entry_reference` as the cross-retrieval matching field when usable, but it is optional and its FAQ explicitly describes ASPSPs that omit it or return duplicates. `transaction_id` is a details-fetch identifier, not a stable deduplication key.

OP's own PSD2 API documents an important account-type distinction: current-account transactions and card transactions use separate endpoints and schemas. The current-account schema has `archiveId`, which OP explicitly says can repeat for related transactions. The card-transaction schema documents description, amounts and two dates, but no transaction-level ID or status. This does not prove which OP endpoint Enable Banking uses or how it maps OP fields to its unified transaction schema.

Consequently, the docs support neither a conclusion that OP credit-card IDs are missing/unstable in Enable Banking nor a conclusion that repeated-looking Actual rows came from any particular layer. The decisive OP-specific mapping and lifecycle facts remain unknown.

## Findings by evidence level

### Enable Banking: documented semantics, with explicit exceptions

- In the [API schema](https://enablebanking.com/docs/api/reference/#transaction), `entry_reference` and `transaction_id` are optional fields. The schema describes `entry_reference` as an ASPSP-provided unique and immutable reference for an account across sessions, but the [FAQ's qualifications](https://enablebanking.com/docs/faq/#are-there-unique-identifiers-for-transactions) matter: references are available for most, not all, ASPSPs; some provide none and some provide duplicate values. References are not globally unique across accounts. Enable Banking says references are immutable for the same account identification hashes, but this is not a universal guarantee that every returned value is present or collision-free.
- Enable Banking says it sometimes generates synthetic `entry_reference` values when an ASPSP lacks a usable ID, subject to conditions. It does not identify in public docs whether OP credit-card records qualify, which source fields are used, or what a particular OP record's reference represents.
- `transaction_id` is explicitly for requesting [transaction details](https://enablebanking.com/docs/api/reference/#get-transaction-details). Enable Banking says it can be null/omitted, is supplied only when details are available, may change when the transaction list is fetched again, and must not be used as a unique transaction key ([FAQ](https://enablebanking.com/docs/faq/#what-is-the-difference-between-entry-reference-and-transaction-id-transaction-properties)).
- Pending records are not a dependable identity source. Enable Banking says that before settlement, transaction properties can change or the transaction can be cancelled. References are usually supplied only for `BOOK` records. A `PDNG` reference is returned only where the ASPSP supplies a unique pending reference that remains unchanged when booked; otherwise Enable Banking advises excluding pending rows from matching ([FAQ](https://enablebanking.com/docs/faq/#are-there-unique-identifiers-for-transactions)).
- The docs do not promise that descriptions or dates remain constant across fetches. The [Enable Banking synchronization article](https://enablebanking.com/blog/2024/10/29/how-to-sync-account-transactions-from-open-banking-apis-without-unique-transaction-ids) is guidance, not a per-ASPSP contract: it recommends treating amount, direction and booking date as stable for already-booked (`BOOK`) rows, while acknowledging that properties may change across PSD2 processing layers and recommending fuzzy matching for other fields. It gives no OP-card-specific guarantee.

### OP: documented differences between account and card transaction resources

OP's [PSD2 AIS product page](https://op-developer.fi/products/banking/op-psd2-account-information-service-api) says the product exposes current accounts and transactions as well as credit cards and card transactions. Its [v1.1 API reference and OpenAPI schema](https://op-developer.fi/docs/api/3VvR5an0qoV4y41EGLSqfb/PSD2%20AIS) document these as distinct resources:

| OP resource                              | Documented transaction fields relevant here                                                                                     | What the docs do and do not establish                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /accounts/{accountId}/transactions` | `archiveId`, message/reference, amount, `bookingDate`, `valueDate`, `paymentDate`, payer/recipient, and proprietary description | `archiveId` is generated by the bank, but OP explicitly says two or more related transactions with different recipients may share it. Thus it is not guaranteed one-to-one with a transaction. OP defines the three dates with distinct meanings.                                                                                                             |
| `GET /cards/{cardId}/transactions`       | Description, amount/currency, optional original amount/currency, `postingDate`, and `transactionDate`                           | The documented `CardTransaction` schema has no transaction-level ID or status field. The separate `cardId` is described as a unique surrogate for the **authorized card**, not an ID for an individual transaction. The schema does not promise that returned rows/descriptions/dates are immutable or state whether open authorizations appear in this list. |

OP's card schema separately defines `statementBalance` as used credit excluding open authorizations, with `authorizedOutstandingAmount` holding those open authorizations. That is a documented credit-card-specific balance distinction, **not** a guarantee about transaction-row status or pending-to-booked matching.

The OpenAPI examples are schemas/examples, not proof that all fields are populated or that a production connector emits exactly those shapes. In particular, no public OP or Enable Banking source located for this research specifies whether Enable Banking's OP connector reads OP's card endpoint, maps OP `archiveId` to Enable Banking `entry_reference`, creates a synthetic reference, or returns no reference for those records.

### Paging and repeated fetches

- Enable Banking's generic transaction endpoint accepts inclusive `date_from` and `date_to` dates and a `continuation_key` ([API reference](https://enablebanking.com/docs/api/reference/#get-account-transactions)). The FAQ says to repeat requests with the same other query parameters until no continuation key remains; page size varies by ASPSP and account, and even an empty page may have a continuation key ([FAQ](https://enablebanking.com/docs/faq/#how-does-transaction-fetching-with-a-continuation-key-work)).
- The continuation key is only valid in the current session. Enable Banking says it does not store/cache the account data. The documentation describes pagination mechanics, but does **not** promise exactly-once rows across pages, deduplication across separate calls, or stable page ordering.
- Because Enable Banking's date bounds are inclusive, two requested date ranges sharing a boundary date both include that date. That is query semantics, not evidence that OP or Enable Banking actually repeats a transaction in a given response. No public source found guarantees deduplication across overlapping date windows.
- OP's account and card transaction endpoints also document continuation tokens. OP's [workflow page](https://op-developer.fi/p/accountauthorizationflow) says a continuation token identifies the point where a page ended; it does not state an exactly-once or cross-request deduplication guarantee. OP's card endpoint has no documented date-window parameters.

### First-party support observation (not OP-specific)

In a public [Actual Enable Banking feedback thread](https://github.com/actualbudget/actual/issues/7799#issuecomment-5687332160), an Enable Banking support representative said some banks change `entry_reference` between pending and booked forms, and described a case where the bank later confirmed an initially pending entry even though both Enable Banking responses had `BOOK` status. The representative recommended fetching booked-only where possible. This is useful corroboration that status and identifiers can be ASPSP-dependent, but it concerns other banks and is not evidence about OP.

### Actual source snapshot (implementation observation, not a deployment claim)

At the researched base commit [`33912a083`](https://github.com/actualbudget/actual/tree/33912a083), Actual's Enable Banking normalizer prefers `entry_reference`, falls back to `transaction_id`, and then derives a local content-based ID if both are absent. It chooses `booking_date`, then `value_date`, then `transaction_date` for its normalized date; it marks only `PDNG` as pending. The current service requests a date window and accumulates continuation pages. These are facts about that source snapshot only; they do not prove the behavior of the user's deployed client/server or identify which OP field Enable Banking returns. See [`enablebanking-service.ts`](https://github.com/actualbudget/actual/blob/33912a083/packages/sync-server/src/app-enablebanking/services/enablebanking-service.ts#L213-L333) and [paging](https://github.com/actualbudget/actual/blob/33912a083/packages/sync-server/src/app-enablebanking/services/enablebanking-service.ts#L477-L530).

## Unknowns that remain material

1. Which OP production endpoint Enable Banking uses for a credit-card account, and the exact OP-to-Enable-Banking field mapping.
2. Whether OP card records exposed through Enable Banking have `entry_reference` or `transaction_id`, and, if so, whether the reference is ASPSP-issued or synthetic and whether it remains stable across fetches/sessions.
3. Whether OP exposes card authorizations as `PDNG`, `BOOK`, another status, or not as transaction rows; whether a posted row replaces an authorization; and whether the two forms share an identifier.
4. Whether OP/Enable Banking changes a card record's amount, date, description, counterparty/remittance, or identifier between repeated fetches, and whether identical records can occur across pages or overlapping windows.

## Sharp next question

Can OP or Enable Banking state which OP card endpoint/fields feed the unified Enable Banking transaction response, specifically whether `entry_reference` on an OP card row is stable across its authorization-to-posting lifecycle? If no public answer exists, the next useful observation would be a privacy-reviewed, sanitized pair of raw Enable Banking responses for one card transaction across repeated syncs, with page/window parameters and a debit-account control. Documentation alone cannot answer that mapping question.
